# Лабораторная работа 2: потоки, процессы и асинхронность

В работе реализованы три варианта подсчета суммы от 1 до `10_000_000_000_000` и три варианта параллельного парсинга страниц с сохранением заголовков в PostgreSQL из лабораторной 1.

## Структура

```text
lab2/
  sum_threading.py          # threading
  sum_multiprocessing.py    # multiprocessing
  sum_async.py              # asyncio
  parse_threading.py        # requests + threading
  parse_multiprocessing.py  # requests + multiprocessing
  parse_async.py            # aiohttp + asyncio
  benchmark_sums.py         # единое сравнение времени
  benchmark_parsers.py      # единое сравнение парсеров
  common.py                 # разбиение данных, HTML и сохранение в БД
```

Результаты парсинга сохраняются в таблице `parsed_pages`. Она связана с `users` отношением one-to-many и создается миграцией `20260915_0002`.

Сохраненные текущим пользователем строки можно проверить через защищенные эндпоинты `GET /parsed-pages` и `GET /parsed-pages/{page_id}`.

## Запуск

Сначала запустите API и PostgreSQL и примените миграции:

```bash
docker compose up -d --build
```

Подсчет требуемой суммы всеми способами:

```bash
docker compose exec api python -m lab2.benchmark_sums
```

Для демонстрации CPU-нагрузки без формулы можно взять выполнимый диапазон:

```bash
docker compose exec api python -m lab2.benchmark_sums --limit 10000000 --algorithm loop
```

Парсеры запускаются отдельно:

```bash
docker compose exec api python -m lab2.parse_threading
docker compose exec api python -m lab2.parse_multiprocessing
docker compose exec api python -m lab2.parse_async
```

Свои URL можно передать позиционными аргументами. Для потоков и процессов число исполнителей задается `--workers`.

Все три парсера и итоговая таблица времени запускаются одной командой:

```bash
docker compose exec api python -m lab2.benchmark_parsers
```

## Важное замечание о сравнении

Для диапазона до `10^13` используется формула арифметической прогрессии внутри каждой подзадачи. Результат точный, однако вычисление настолько короткое, что измеряется главным образом стоимость создания потоков, процессов и asyncio-задач. Режим `--algorithm loop` нужен для наглядного CPU-bound сравнения на меньшем диапазоне: GIL не дает Python-потокам выполнять Python-код одновременно, процессы используют несколько ядер, а asyncio само по себе не распараллеливает вычисления.

Для сетевого парсинга потоки и asyncio перекрывают время ожидания ответа. Процессы тоже работают параллельно, но требуют больше памяти и времени на запуск.

Контрольный замер требуемого диапазона на macOS, Python 3.14.5, 4 исполнителя:

| Подход | Результат | Время, с |
| --- | ---: | ---: |
| threading | 50000000000005000000000000 | 0.000275 |
| multiprocessing | 50000000000005000000000000 | 0.288773 |
| asyncio | 50000000000005000000000000 | 0.000099 |

Для формулы выигрыш от параллелизма отсутствует: полезная работа занимает меньше времени, чем создание исполнителей. Точные значения зависят от компьютера и текущей нагрузки, поэтому скрипт `benchmark_sums.py` печатает новую таблицу при каждом запуске.

Контрольный сетевой замер четырех URL на том же компьютере (изолированная SQLite-база использовалась только вместо недоступного локального Docker daemon):

| Подход | Сохранено страниц | Время, с |
| --- | ---: | ---: |
| threading | 4 | 0.775 |
| multiprocessing | 4 | 0.726 |
| asyncio | 4 | 0.505 |

В целевом запуске таблица `parsed_pages` находится в PostgreSQL из `docker-compose.yml`. Сетевые значения зависят от задержки сайтов и при повторном запуске будут отличаться.
